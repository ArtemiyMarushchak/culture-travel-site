## 1. Главный вопрос: нужен ли тебе monorepo?

### Что такое monorepo (строго)

**Один git-репозиторий → несколько независимых пакетов** с отдельными `package.json`:

```
culture-travel/                    ← корень monorepo
├── apps/
│   └── site/                      ← сайт culture-travel.ru
├── packages/
│   ├── tokens/                    ← @culture-travel/tokens
│   ├── build/                     ← сборщик
│   └── blocks/                    ← блоки как npm-пакет
├── package.json                   ← workspaces: ["apps/*", "packages/*"]
└── pnpm-workspace.yaml
```

Нужны: **Node.js, pnpm/npm, Turborepo/Nx** (опционально), CI для сборки пакетов.

### Что у тебя сейчас

**Один сайт, один сборщик, одна дизайн-система** — это **модульный монолит** (хорошая структура в одной папке):

```
culture-travel-site/
├── core/           ← ядро
├── blocks/         ← блоки
├── content/        ← JSON контент
├── styles/tokens/  ← CSS токены
├── tools/build.mjs ← сборка
└── dist/           ← результат
```

### Моё честное мнение

| Вариант | Когда имеет смысл | Для тебя сейчас |
|---------|-------------------|-----------------|
| **Модульный монолит** (текущий) | 1 сайт, 1 человек, статика | ✅ **Рекомендую** |
| **Monorepo apps/packages** | 2+ сайта, админка, npm-библиотека | ❌ Рано, лишняя сложность |
| **Monorepo «на будущее»** | Планируешь 3 проекта через 6 мес | ⚠️ Можно заложить, но не сейчас |

**Вывод:** называть это «monorepo» можно условно — **логически разделённый один проект**.  
Настоящий monorepo с `apps/` и `packages/` **не нужен**, пока нет второго приложения.

Перенос всего в `apps/site/` **сломает пути**, потребует Node/npm, не даст SEO/безопасности/удобства JSON — только другую структуру папок.

## 2. Рекомендуемая архитектура (на согласование)

### Вариант A — «Модульный монолит» ✅ рекомендую

Остаёмся в `culture-travel-site/`, усиливаем границы:

```
culture-travel-site/
│
├── core/                      ← СЕРДЦЕ (JS + конфиг)
│   ├── site.json              глобальные настройки
│   ├── nav.json               меню
│   ├── blocks.registry.json   каталог блоков
│   ├── registry.js            init-функции блоков
│   ├── init.js                boot в браузере
│   ├── anchors.js
│   └── video-overlay.js
│
├── blocks/                    ← UI (независимые модули)
│   └── {name}/
│       ├── {name}.html
│       ├── {name}.css
│       └── {name}.js          опционально
│
├── content/                   ← ТО, ЧТО РЕДАКТИРУЕШЬ ТЫ / AI
│   ├── cases/
│   │   ├── _template.json     шаблон для нейросети
│   │   └── safari.json        каждый кейс = отдельный URL
│   ├── news/
│   └── hotels/
│
├── pages/                     ← статические страницы (главная, отели…)
├── templates/                 ← шаблон блоков для content-страниц
│
├── styles/
│   ├── tokens/                ← цвета, шрифты, отступы (МЕНЯЕШЬ ЗДЕСЬ)
│   ├── ui/                    ← классы .ui-h1 …
│   ├── foundation/
│   └── main.css               ← одна точка входа
│
├── assets/
│   └── fonts/montserrat/      ← CDN сейчас, woff2 позже
│
├── seo/                       ← head, defaults, JSON-LD
├── layouts/                   ← default.html
├── tools/build.mjs            ← сборщик
├── preview/                   ← превью токенов (локально)
└── dist/                      ← только результат (не в git)
```

**Плюсы:** просто, всё локально, не нужен npm для работы с JSON, build — один файл.  
**Минусы:** нет «изоляции» npm-пакетов (она тебе пока не нужна).

### Вариант B — «Настоящий monorepo» (если настаиваешь)

```
culture-travel/
├── apps/site/                 ← весь текущий проект переезжает сюда
├── packages/tokens/           ← только CSS variables
├── packages/build/            ← build.mjs как пакет
└── package.json
```

**Плюсы:** масштаб на 3+ проекта, общие tokens между сайтами.  
**Минусы:** миграция 2–3 дня, все пути меняются, Node обязателен, для одного сайта — overkill.

**Моя позиция:** B — только когда появится **второй** сайт или админка.

## 4. Безопасность — практически

| Риск | Как закрываем | Честно |
|------|---------------|--------|
| Секреты в git | `.env` не используем; только `site.json` без паролей | ✅ Статика = мало attack surface |
| XSS из JSON | Build экранирует `{{key}}` через `escapeHtml` | ✅ Кроме полей `body`/`content` — там доверяем себе |
| CSP | В `head.html` уже есть Content-Security-Policy | ⚠️ Kinescope iframe потребует `frame-src` позже |
| Зависимости | **Нет npm в runtime** — сайт = HTML/CSS/JS | ✅ Компьютер не страдает |
| GitHub | Private repo, deploy только через Actions | ✅ См. `docs/SECURITY.md` |
| Локальная работа | `python3 -m http.server` — только читает файлы | ✅ Ничего не устанавливает |

**Что НЕ делаем:** не ставим случайные npm-пакеты, не запускаем `curl | bash`, не храним API-ключи в JSON.

## 5. SEO — как легко продвигать

| Механизм | Как работает | Почему хорошо |
|----------|--------------|---------------|
| **Статический HTML** | build → готовые страницы | Google видит текст сразу, быстрый TTFB |
| **Чистые URL** | `/cases/safari/` не `?id=1` | Человекочитаемо, индексируемо |
| **Уникальный контент** | каждый JSON = свой title, description, og | Кейсы и новости **не дубли** |
| **JSON-LD** | Organization, Article, Breadcrumb | Rich snippets |
| **sitemap.xml** | build генерирует | Яндекс/Google находят страницы |
| **llms.txt** | для AI-поиска | Современный SEO |
| **404 noindex** | `robots: noindex` в meta | Не индексируем мусор |

### Независимые страницы (твой главный запрос)

```
content/cases/_template.json   ← шаблон полей
content/cases/maldives.json    ← уникальные фото, текст, video
         +
templates/case.page.json     ← какие блоки на странице
         +
build.mjs
         ↓
dist/cases/maldives/index.html ← СВОЙ URL, СВОЙ SEO, СВОЙ контент
```

То же для `content/news/`. **Страница не ломает главную** — другой slug, другой JSON, тот же шаблон блоков.

## 6. JSON + нейросеть — сценарий редактирования

```
1. Открываешь content/cases/_template.json
2. AI генерирует новый файл по шаблону (slug, title, seo, body, media)
3. Кладёшь в content/cases/new-trip.json
4. node tools/build.mjs
5. Готово: /cases/new-trip/
```

**Что улучшим позже (не сейчас):**
- JSON Schema (`content/cases/_schema.json`) — AI и build проверяют поля
- Скрипт `tools/validate.mjs` — ловит ошибки до деплоя

**Цвета/дизайн** — не в JSON страниц, а в `styles/tokens/colors.css`.  
Один файл → весь сайт меняет палитру. Это правильно: контент отдельно, дизайн отдельно.

## 7. JS-ядро — сердце проекта

### Сейчас

```
init.js → registry.js → initHeader, initHeroVideo, …
       → anchors.js
       → video-overlay.js
```

### Куда развиваем (согласовать)

```
core/
├── init.js              orchestrator (только boot)
├── registry.js          blockInits map
├── blocks.registry.json метаданные (build + docs)
├── events.js            ← шина событий между блоками (если нужно)
├── site.json
└── runtime/
    ├── anchors.js
    └── video-overlay.js
```

**Принципы ядра:**
1. Блок **не знает** о других блоках напрямую
2. Init получает только свой DOM-узел `[data-block]`
3. Общее (scroll, anchors) — в `core/`, не в блоках
4. Build **не** выполняет JS — только копирует в dist
